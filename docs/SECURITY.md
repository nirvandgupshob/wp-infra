# Безопасность

## Доступ

Долгоживущих ключей AWS в GitHub нет. Actions аутентифицируется через OIDC: каждый запуск получает короткоживущий подписанный токен, а AWS меняет его на временные учётные данные.

Доверие выписано в неизменяемом формате субъекта:

```
repo:nirvandgupshob@158572548/wp-app@1345383465:environment:production
```

Пять ролей, каждая привязана к одному репозиторию и одному окружению GitHub:

| Роль | Права |
|---|---|
| `wp-gh-terraform-plan` | `ReadOnlyAccess` плюс расшифровка ключом state |
| `wp-gh-terraform-apply-staging` | `PowerUserAccess` плюс IAM в пределах ролей `wp-*` |
| `wp-gh-terraform-apply-production` | то же, доступна только из окружения `production` |
| `wp-gh-deploy-staging` | push/pull в ECR, деплой ECS, чтение state и логов |
| `wp-gh-deploy-production` | то же плюс `CreateDBClusterSnapshot` на кластере production |

Роли production примеряются только из окружений GitHub, требующих подтверждения.

## Секреты

Ни один пароль не попадает в Terraform state.

Пароль мастера базы генерирует и ротирует сам RDS (`manage_master_user_password`), Terraform его не видит: в state `master_password` равен `null`.

Пароль администратора WordPress порождается блоком `ephemeral "random_password"` и пишется в Secrets Manager через `secret_string_wo` — провайдер отправляет значение в API, не сохраняя его. В выгруженном state `secret_string` пуст, `secret_string_wo` равен `null`.

В контейнер секреты приходят через блок `secrets` в описании задачи с указанием ключа JSON, поэтому подставляется одно поле, а не документ целиком.

Бакет со state версионируется, шифруется собственным ключом KMS, полностью закрыт от публичного доступа и отклоняет запросы без TLS.

## Сеть

Security groups ссылаются друг на друга, а не на диапазоны адресов:

```
ALB    80, 443  из интернета
ECS      8080   только из группы ALB
Aurora   3306   только из группы ECS
EFS      2049   только из группы ECS
```

У Aurora нет исходящих правил вообще база, ничего не инициирует сама.

База и файловая система живут в isolated-подсетях, в таблицах маршрутов которых есть только локальный маршрут VPC. Пути в интернет и обратно нет независимо от того, что настроено в security groups.

Flow logs VPC уходят в CloudWatch. Без них отброшенный пакет невидим: security group отбрасывает молча, а приложение видит только таймаут.

## Приложение

Контейнер работает от uid/gid 33 на порту 8080 — ничего внутри не выполняется от root, и право занимать привилегированный порт не требуется.

| Настройка | Что даёт |
|---|---|
| `DISALLOW_FILE_MODS` | нельзя установить плагин или тему и править код из админки |
| `WP_HTTP_BLOCK_EXTERNAL` | WordPress не делает исходящих HTTP-запросов |
| `AUTOMATIC_UPDATER_DISABLED` | версия та, что заявлена в образе |
| `FORCE_SSL_ADMIN` | сессионные куки админки только по HTTPS |
| `WP_DEBUG_DISPLAY = false` | ошибки уходят в лог, а не на страницу |

Весь код, включая ядро WordPress, запечён в образ. Записываемым остаётся только `wp-content/uploads`. Темы по умолчанию удаляются при сборке: неактивная тема эксплуатируется так же, как активная.

Базовые образы зафиксированы дайджестом, а не тегом. Trivy сканирует собранный образ на каждом pull request, и пайплайн падает на находках HIGH и CRITICAL. В ECR включены неизменяемые теги и сканирование при загрузке, поэтому после ревью тег нельзя перевесить на другое содержимое.
